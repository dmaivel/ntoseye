## Unreleased

Stops and `u` now show where the code goes: the instructions around the stop in its function, jump and call targets by name, the jumps between them drawn as arrows, and whether the next one is taken. A bugcheck stop shows the registers the faulting instruction ran with, and its stack starts at the frame that faulted.

### Added

- `--kd-handshake-timeout <seconds>` sets how long the `kd` and `kdnet` backends wait for the target's first answer, as `NTOSEYE_KD_TIMEOUT` does, and wins over it; the default is still 8 seconds. MCP's `open` takes it as `kd_handshake_timeout`, DAP's attach arguments as `kdHandshakeTimeout`, and the SDK as `ntoseye.attach(kd_handshake_timeout=...)`.
- The `gdb` backend sets as many hardware breakpoints (`ba`) as the GDB stub accepts, no longer four, so QEMU running with TCG, which emulates them, takes any number. Under KVM the processor still has four debug registers, and a fifth `ba` says the stub refused it.
- A module whose PDB no symbol source has — a vendor driver never published — falls back to the export table of its image in the dump, as the Windows debugger does, so `k`, `ln` and `!analyze` name its functions (`myfault!nmf_fault_irql+0x35`) where they showed `module+offset`, and a deferred breakpoint on an export binds. So does a module whose image names no PDB at all (no CodeView record), once fetching the image does not name one either. A PDB acquired later (a source added, the process attached again) replaces the export symbols.
- The prompt suggests as you type: the rest of the most recent earlier line that starts with what you've typed appears dimmed after the cursor (`b` suggests `bp nt!NtClose`), as fish does. **→**, **End** or **Ctrl+E** accepts it, **Ctrl+→** a word at a time; **Enter** runs only what you typed. Tern's prompt already did this. With `NO_COLOR` set, nothing is suggested, since only its dimming sets a suggestion apart from what you typed.
- The prompt marks where each command and its output start and end (OSC 133), as a shell does for its terminal, so a terminal that reads the marks can jump between commands, select one's output, or flag one that reported an error.
- When the target ran for 10 seconds or more before it stopped, the terminal shows a desktop notification of the stop (`ntoseye: breakpoint #0 hit at nt!NtClose on processor 2`): kitty only while its window is out of view, terminals that read OSC 9 (Ghostty, iTerm2) each time. A stop you cause with Ctrl+C or `break` sends none.
- The window title names the prompt's processor and backend, and where the target stopped or that it runs (`ntoseye - 3: kd - nt!NtClose+0x5`), and is given back on exit.
- A stop at an `int3` that Windows executes on purpose says why it broke in. The first is a resource timeout: when a thread waits for an executive resource (ERESOURCE) longer than the timeout, Windows breaks in at `nt!ExpWaitForResource`, and the stop now says so and points to `!locks`.
- `!runaway [flags]` shows how much processor time each thread of the current process has used, most first, as WinDbg's does: user-mode time (`1`, the default), kernel-mode time (`2`), and time since the thread started (`4`). It works on a kernel target, from each thread's tick counts, and on a user-mode minidump, from its thread-info stream. The SDK has it as `Process.thread_times()` and `UserProcess.thread_times()`.
- `!cs [-l] [address]` lists the critical sections of the current process, as ntdll keeps them on `RtlCriticalSectionList`, or shows one: whether a thread holds it, the owner's TID, its recursion count, how many threads wait for it, and how often threads have waited. `-l` lists only the held ones. It works on a kernel target and on a user-mode minidump; the SDK has `Process.critical_sections()` and `critical_section(address)`, and the same on `UserProcess`.
- `sxe ld:<module>` and `sxn ld` apply to the user-mode DLLs and executables that processes map, and a deferred `bu /p <pid> <module>!<symbol>` is armed in that process as the module is mapped, before its entry point runs. A trap at `nt!PsCallImageNotifyRoutines`, in place only while such a filter or breakpoint waits, sees every mapping in every process, on KD, KDNET, and the `gdb` backend; no global flag is needed. The module's symbols load from the image, and a breakpoint in a page the process has not touched yet goes to the target's breakpoint table, which writes it when the page arrives.
- `.dump /u <file>` writes a user-mode minidump of the current process, from a live target or a kernel dump: its threads with the user-mode registers their stacks give, their names and priorities; its modules with their CodeView records and versions; the modules it unloaded; its handles, named; its regions as `VirtualQuery` reports them; every committed page of its memory that is in physical memory or was never touched; the build string and time-zone bias; and, when the target stopped at an exception that one of its threads raised in user mode, that exception, so `.ecxr` and `!analyze` work on the minidump. `ntoseye --dump` and other minidump readers open it, and the SDK has it as `Process.write_minidump(path)`.
- Reads of process memory that Windows compressed into its memory-compression store (Windows' default on client editions) decompress the page from the store, where they failed: on the `memory` backend and on `kd`/`kdnet` with the host memory source, for 64-bit Windows 10 1703 and later whose PDB types the partition's store fields. `ntoseye` reads the store's layout from the kernel's code on first use, since the PDB does not describe it and it moves between releases (and within 24H2's servicing). `.dump /u` captures these pages too. See [Compressed memory](docs/using/memory.md#compressed-memory).

### Changed

- **Breaking:** A processor is named by its number, counted from 0 as Windows counts them, the same on every backend: the prompt reads `3: kd>`, as WinDbg's does, a stop names `processor 3`, and `~` lists the processors by number. They were the backends' thread IDs, `p1.4` over `kd` and `p01.04` over `gdb`, counted from 1 in hex. In a guest partition's view, a VP is that guest's processor, under the prompt `1: partition 0x3>`, and a user-mode dump's prompt names the thread by its number in `~`'s list (`17: minidump>`), as WinDbg's `0:017>` does. `~` and `vcpu` take only the number (`~3s`); `~p01.04s` is gone. MCP's trailer and the thread names of DAP and gdbserver clients name processors the same way.
- On an ARM64 target, `rip` and `rsp` no longer name `pc` and `sp`: `r`, expressions and breakpoint conditions take the ARM64 names (`@pc`, `@sp`, or `$ip` and `$csp` on any architecture), as WinDbg does. `fp`, `lr` and `pstate` still name `x29`, `x30` and `cpsr`.
- On an ARM64 target, `!vtop` with a directory base lists each page-table entry the translation reads, with its flags, as it does on AMD64. It showed only the physical address.
- On an ARM64 target, `ba e` refuses an address that is not 4-byte aligned when you set it, on every backend, as such a breakpoint never fires. Only the `kd` backend refused it, and only once it programmed the processors.
- A stop's disassembly shows nine instructions around the instruction pointer, those before it too, within its function (no longer the padding past its `ret`), each with its offset from its symbol, as the stack and `ln` count it; where a symbol starts among them, a line names it (`nt!KiSystemServiceCopyEnd:`). A direct jump or call names its target in place of its address: by its offset when the target is among the instructions shown, under the same symbol (`je +0x33`), else by its symbol, which `u`, `bp` and `g` take as it is (`call nt!ObpPushStackInfo`, `jle ↓ nt!ObfDereferenceObject+0x59`). The jumps between the instructions shown are drawn as arrows, a breakpoint is marked `●`, and the instruction the processor is at says whether its jump is `taken` (its arrow lit) or `not taken`, and where a `ret` returns to. The instruction bytes are left out of the stop; `u` shows them. MCP's step results show the same.
- `u`, `ub` and `uf` list instructions as the stop does, with their bytes, and mark the instruction the selected thread is at. `uf` draws the arrows across the whole function. A short jump now names its target, where it showed a bare address.
- At a bugcheck stop, the registers are the ones the faulting instruction ran with: those of the trap frame at the fault (one the parameters name, or the innermost trap on the stack, which a 0xD1 or 0x50 is raised from), with those a trap frame does not save, such as `rbx` and `r12`-`r15`, recovered by the stack walk. The heading says `registers (trap frame)`, `registers (unwound)`, or `registers (at stop)` for the processor's where neither is found. The stack starts at the frame that faulted, the bugcheck's own frames folded into one line (`00–05  nt!DbgBreakPointWithStatus … nt!KiPageFault+0x468`).
- Stacks (the stop's, `k`, `!thread`, `!analyze -v`) mark with a line where the walk crosses from kernel code into the user-mode code that called it (`user mode`) or through a trap or an interrupt (`trap`).
- A frame's source line in `k` reads as in the stop, `[local <path>:<line>]` for the copy `.srcpath` maps, `[recorded <path>:<line>]` otherwise. In a terminal that supports links, a local copy that matches the PDB, and the file `ls` and `lsa` list, are links that open it.
- `dqs`, `dps`, `dds` and `kd` name the registers that point into each slot (`rsp ▶`), and mark a value that is a return address, one the code before ends in a call, `↩` before its symbol.
- `db` splits each row's two halves with `-`, as WinDbg does, and the memory displays show zero values and unreadable items dimmer than data.
- `~` marks the selected vCPU with `.`.
- On an ARM64 target, the register grid names the flags `cpsr` has set after its value (`cpsr 0000000060000000 [Z C]`), as it names `rfl`'s on AMD64. They were spelled under its digits, on a line of their own.
- `r rfl` reads AMD64's flags register by the name the grid shows, and a selected frame's or context's registers answer to their other names too (`rfl` for `eflags`, `fp` for `x29`). `r eax` in a frame that did not save `rax` says it was not recovered rather than that no such register exists.
- One blank line sets a command's output apart from the next prompt, whatever the command ended with: some commands left none, others one or two. The output starts right under the command line, and the blank lines between its sections stay. A `.logopen` transcript reads the same; MCP results, gdbserver's `monitor` output and DAP's debug console end at the output's last line.
- Every command's output follows one style, closer to WinDbg's. One object's fields are aligned under a heading that names it (`THREAD`, `PROCESS`, `TEB`, `TOKEN`, as WinDbg names them); a value that is missing or could not be read is `-`, with the reason in one note under the block; booleans read `yes`/`no`, enumerations `Waiting (0x5)`, flag sets `0x8004 (SE_DACL_PRESENT | SE_SELF_RELATIVE)`, times `2026-10-15T23:23:28Z`, and processes `smss.exe (PID 540)`. Messages start in lowercase, an empty result says what there is none of, and a command that changed nothing says so (`.logclose` with no log open, `.cxr` with no context selected). `!thread` and `!process` list their fields one per line, not packed into `key=value` runs, and many extension commands (`!vm`, `!locks`, `!lookaside`, `!stacks`, `!idt`, `!gdt`) lay out their records as tables. Disassembly prints hex in lowercase.
- Stacks are numbered as `k` numbers them (`00`, `01`) everywhere, the stop's and `!thread`'s too, and every stack in `k`'s layout has its header row (` # Child-SP  IP  Call Site`). A frame without a symbol shows its address in the call site, and a stop names its thread as `!thread` does (`thread ffffb10918a7f080  TID 10236  PID 6532  process svchost.exe`).
- `r` with a frame or a context selected shows the register grid, with `-` for a register the frame did not save, as plain `r` does. It listed the registers one per line, sorted by name as text.
- A bad argument to a hypervisor command (`!hvvps`, `!hvept`, `!hvcalls`, `!hvd`, `.partition` and the others) says which argument is wrong, then the usage line. They printed the whole help text.
- `attach` and `.process /i` also select a thread of the process, so `!teb`, `!gle`, and `k` show it without a `.thread`: the thread a processor runs, with its live registers, else its first whose kernel stack is resident. They say which they selected. `.process` without `/i` still keeps the current thread, as WinDbg's does.
- `threads` with no filter, while attached to a process, lists that process's threads, as `!for_each_thread` and `!uniqstack` do; `threads *` lists every thread. Its start address is the thread's own entry (its Win32 start address, such as `ping!wmainCRTStartup`), named where symbols are loaded, the kernel's and the attached process's. It showed `StartAddress`, which for a process's first thread is a pool address, unnamed.
- `!locks` walks the whole system resource list and shows the resources that are held, as WinDbg's does, each with whether it is owned exclusively or shared and its owners' TIDs and processes; `!locks -v` shows every resource. It showed the first 256 resources, held or not, which on a system with tens of thousands of resources rarely included the one that blocks. A walk of 65,000 resources takes a few seconds, as each is read once.

### Fixed

- On the `kd` and `kdnet` backends, `r` shows a hardware breakpoint set or cleared with `ba`/`bc`, or an MSR written with `wrmsr`, as soon as you make the change. It showed the debug registers and `efer` as they were before, until the target ran again.
- On an ARM64 target, `p` steps over a pointer-authenticated call (`blraa`, `blrab`, `blraaz`, `blrabz`), as it steps over `blr`, instead of into it.
- Modules are named after their image file, as WinDbg's `lm` names them, not the loader's alias for it: `kd.dll` rather than `kdcom.dll`, `mcupdate_GenuineIntel.dll` rather than `mcupdate.dll`, in a WOW64 process's 32-bit module list too. Their `module!` prefixes follow (`kd!`, `mcupdate_genuineintel!`).
- A stop after `p` or `t` marks the registers the step changed even when the thread finished the step on another processor (processor 0 before, processor 3 after), as it often does on a busy guest. The stop marked none then, and MCP's step result showed the whole stop instead of what changed.
- A guest's debug output (`DbgPrint`), printed as the target runs and by `!dbgprint`, shows control characters as visible symbols, such as `␛` for an escape, instead of passing them to the terminal, so a driver's output can no longer move the cursor, recolor or clear the screen, retitle the window, or plant a link. The SDK's `debug_log()` still returns the text as the guest printed it.
- A WHEA_UNCORRECTABLE_ERROR (0x124) and a KERNEL_SECURITY_CHECK_FAILURE (0x139) are described in a full sentence, in the bugcheck stop, `!analyze -show` and the SDK's `BugcheckAnalysis.description`, instead of starting mid-sentence with "and indicates that".
- With `NO_COLOR` set, the prompt and its completion menu are plain too, as the rest of the output already was.
- With `TERM=dumb`, as in Emacs's `M-x shell`, ntoseye reads commands line by line as with `--plain-repl` and prints no color or other escape sequences, which such a terminal showed as stray characters.
- `!handle`'s Object column, and the SDK's `HandleEntry.object`, hold the object, as WinDbg's does and as `!object` and `!fileobj` take it. They held its header, 0x30 bytes before it.
- `!exqueue` lists the work queues on Windows 11 build 26200, which keeps one flat list of them per partition. It read the list as one per NUMA node and failed on every queue.
- `!heap -x` says which heaps it could not search instead of concluding that the address is in no heap.
- `vertarget` reads `Windows 10.0`, from the shared user data page, instead of `Windows 15.26200`, which took the dump header's build-type marker for a version.
- On a processor whose context a dump did not capture, `k` says so; it showed a frame at address 0.
- `!error` no longer names a code it does not know with a made-up constant (`STATUS_UNKNOWN`, `ERROR_UNKNOWN`), and says when a value can't be a Win32 error. The SDK's `ErrorCode.name` is empty for such a code.
- The working-set sizes of `!vm` and `!memusage`, and the SDK's `ProcessMemoryUsage.working_set_size`, are in bytes, as the other counters are. They were page counts.
- `s` counts the bytes it could not read correctly, and says so when it could read none of the range rather than reporting no matches. `dS` no longer reads past a string's `MaximumLength`.
- `!hvcall` on a target without direct host RAM, such as a kernel dump, says that the hypervisor's memory needs it, as the other hypervisor commands do. It said the processor was not halted in the hypervisor.
- `!address -summary` on a user-mode dump without a memory-info list prints the summary only, not every captured range.
- `ntoseye mcp --http <address> --unsafe-http` answers requests addressed to the host's network address or name. Since v0.49.1 it refused every request whose `Host` was not a loopback name with `403 Forbidden`, so no other machine could use it.
- On a VBS guest over `kd` or `kdnet`, `bp` in user-mode code that Windows will not let the debugger write, such as ntdll's and kernelbase's, works when `ntoseye` reads the VM's memory from the host: it writes the breakpoint into that memory itself, on x86 guests. So do `p` over a call that returns into such code, and the cleanup of such a breakpoint after a killed session. They failed with `NTSTATUS 0xc0000001` or `bad virtual address`; where the fallback is not available, the error now says that Windows refused the write and what to use instead.
- `ba` takes its options after the access and size too, as WinDbg writes them (`ba e1 /p 4 kernelbase!SleepEx`); it took them only before (`ba /p 4 e1 ...`) and said `/p` was an invalid expression.
- Over `kd` and `kdnet`, `t`, `p` and `pc` step a WOW64 program's x86 code. Windows reports a step there as `STATUS_WX86_SINGLE_STEP`, and each step failed with `target raised exception 0x4000001e while single-stepping`, though it had stepped. `p` over a call to a helper that allocates its caller's frame, such as `_SEH_prolog4` or `_chkstk`, stops after the call instead of running on to the next breakpoint.
- `pt`, `tc`, `pc` and the other walks step over a system call that user-mode code makes (`syscall`, or `int 0x2e`), as `p` does, and go on after it. They stopped with `nt!KiSystemCall64Shadow ... is in ntoskrnl's KVASCODE section`, from planting a breakpoint where the processor enters the kernel.
- `t` and `p` on an instruction that takes long, such as a system call that waits, finish in the stepped thread when another thread hits a breakpoint meanwhile. A hit outside the breakpoint's scope, such as another process's on a `bp /p` site in a shared DLL, is passed over; any other stop, such as an in-scope hit, ends the step there and says what it is. The step ended in the other process, at the breakpoint site, with nothing saying why.
- `gu`, `p` over a call, `tc` and the other walks step a thread of another process than the one `.process` or `attach` selected, such as one a breakpoint stopped in, in that thread's own address space. `gu` said the return address `is not mapped in` the selected process, and the walks failed with `bad virtual address` on the thread's code.
- `k` on a WOW64 thread stopped in its x86 code, as at a breakpoint in x86 `kernelbase`, lists its x86 frames up to `_RtlUserThreadStart`, and `gu` there steps out to the caller. The stack showed only the frame it stopped in, and `gu` said it could not find the caller's return address.
- `!vad` shows each region's commit charge, in pages, on Windows 11 24H2 and later, where the VAD keeps it in a field of its own. It showed `-` for every region.
- `!handle` names the handles whose objects have no name of their own, as WinDbg's does: a file by its path on its device (`\Device\HarddiskVolume3\Windows\System32\en-US\csrss.exe.mui`), a registry key by its path as the hive names it (`\REGISTRY\MACHINE\SYSTEM\ControlSet001\Control\Session Manager`), a process by its image and PID, a thread by its TID and process. They showed `-`.
- `!locks <address>` shows each owner's real acquire count. It showed eight times the count on Windows 10 and later, where the count is a bitfield above three flags.
- Code the compiler split off from a function and placed after a funclet (`$filt$`, `$fin$`) is named after its function, by its function-table entry, in stacks, stops, `u` and `ln`: `nt!ExpWaitForResource+0x4c011f` rather than `nt!KiLockServiceTable$filt$0+0x2fe`, a filter of another function that the address was merely nearest to.
- `!locks` shows an exclusively owned resource with its one owner. It also listed the shared owners its owner table kept from before, as if they owned it too.
- A hardware execute breakpoint (`ba e`) is no longer missed when the stop's DR6 does not say which slot fired, as Windows under KVM reports some hits. Such a hit was taken for a stray single step and resumed, so it faulted again, and could surface as an unexplained single-step exception: a `ba /p` watch on a shared DLL stopped in other processes.
- Over KD, the first `g` no longer stops at once at `nt!DbgBreakPointWithStatus` when ntoseye connected to a guest already halted at a break of its own, such as a user-mode `int 3` or a resource timeout. The kernel kept the break-in the connect sent and took it on its first clock tick.
- Over KD, a user-mode image that Windows reports with `!gflag +ksl` is no longer taken for a kernel module: each one triggered a refresh of the kernel module list, and its base was offered as a hint at where the kernel is.
- Over KD, connecting while a user thread was running (or Windows was stopped in a user process) no longer makes that process the kernel's for the session: ntoseye took the stopped processor's page tables for the kernel's, so the process showed as `kernel`, its addresses went unsymbolized, and its modules showed in every other process. The kernel's are now the System process's.
- Ctrl+C while a filtered breakpoint fires faster than Windows polls for the break-in (a `ba /p` watch on a shared DLL) stops as a pause. After its retries it surfaced as an unexplained single-step exception in whatever process hit the watch last.
- The stack of a WOW64 thread in a user-mode minidump goes on into its x86 frames, from the x86 context its TEB's CPU area saved, as on a kernel target.
- `.dump /u` puts committed pages that the process never touched in the minidump, as the zeros they hold. They were left out as if their contents were unknown: in csrss from the kernel dump, 7 MiB.
- `.dump` writes the whole exception record of the stop into a kernel dump's header: its flags and parameters (an access violation's access type and address) were zeros.
- `dt` reads a word after the type that names one of its fields as that field, as WinDbg does, even when the word would also evaluate: `dt nt!_KPROCESS BasePriority` showed the whole type, because `basepriority` is a pseudo-register. The address may come before or after the fields (`dt nt!_EPROCESS UniqueProcessId <address>`).
- C++ functions and variables of public PDBs are shown and looked up by their undecorated names, as in WinDbg (`sechost!ScDispatcherLoop`, `nt!ST_STORE<SM_TRAITS>::StDmpSinglePageInsert`, `` `string' ``), instead of their decorated names (`?ScDispatcherLoop@@YAXPEAPEAX@Z`).

### Removed

- In Tern, results print as text, as in any other terminal: stops, stacks, memory dumps and the other results Tern drew as cards, tables and trees are text again. Tern's input field, with its completions and palette, stays, and so do the timer while `g` runs and the progress bars of long tasks.

## v0.51.0 (2026-10-19)

### Added

- A local directory on the symbol path (`--sympath-append`, `.sympath+`) supplies the PDBs in its subdirectories too, eight levels down, so a mounted virtio-win ISO's driver PDBs (`viostor/w11/amd64/viostor.pdb`) load without copying them out. ntoseye reads each directory once; `.reload` reads it again for PDBs put there since.

### Fixed

- `!analyze` names the faulting instruction and its driver for a KERNEL_SECURITY_CHECK_FAILURE (0x139) and an UNEXPECTED_KERNEL_MODE_TRAP (0x7F, or 0x1000007F in a minidump), from the trap frame the parameters name or the stack crosses, and buckets the crash and names the culprit by that driver. It named no fault for them, and bucketed them on the instruction the processor stopped at.
- A kernel dump that QEMU wrote (`dump-guest-memory -w`, which libvirt runs when a guest crashes) now opens on the processor that bugchecked, so `!analyze`, `k` and the registers show the crash. ntoseye opened such a dump on processor 0, which on a multiprocessor guest was usually a processor that the bugcheck froze in `nt!KiFreezeTargetExecution`. `!analyze` starts that processor's stack at `nt!KeBugCheckEx`, as for a dump Windows wrote, rather than in the bugcheck callback (pvpanic's) that QEMU's dump was taken in, and no longer takes that callback for the current instruction when it buckets the crash or names a culprit.

## v0.50.0 (2026-10-16)

The Python SDK is now generated from the same definitions as the REPL: each command's SDK method takes the same arguments, runs the same checks, and returns the record the command prints, with the command's help as its docstring. Results are typed records that behave as values, and a stop is one `Stop` hierarchy that `match` and `isinstance()` narrow to the kind of stop and its own parts. Scripts written for v0.49 need changes; the [Python SDK guide](https://ntoseye.com/scripting/sdk/) shows the current API, and the [SDK reference](https://ntoseye.com/reference/sdk/) lists every class.

### Added

- SDK methods for commands that had none: `dbg.inspect.hang()`, `decode_bugcheck()`, `blackbox_bsd()` and the other `blackbox_*()` reports, `session_processes()`, `vtop()`, `set_global_flags()`, `virtio_driver()`, `vring_raw()`, `etw_save()`, `etw_crash_save()` and `etw_crash_session()`; `Memory.pte()`; `Process.inspect()`, `decode_peb()` and `loader_modules()`; `Thread.decode_teb()`; `UserDump.address_report()`, what `!address` shows on a user-mode minidump; and `Breakpoints.list()` and `commands()`, what `bl` and `.bpcmds` show.
- Every SDK handle (`Process`, `Thread`, `Module`, `Cpu`, `Heap`, `Driver`, `Device`, `Breakpoint`, `Trustlet`, `UserThread`, and the hypervisor's) has its record as `info`, each of the record's fields as a property, `to_dict()`, and `==` and `hash` by the object it names and the target it was read from: after the target reloads, an old handle is not equal to a new one for the same object. A process, thread or module handle goes stale when the target reloads, not when its object exits.
- An SDK argument that is a kernel address also takes a debugger expression (`"nt!KiSystemCall64+0x10"`) or the handle of the object there: `dbg.memory.read(proc, 16)` reads the `EPROCESS`, and `dbg.types["nt!_ETHREAD"].at(thread)` makes a cursor on a thread's `ETHREAD`. The handle must come from the same debugger, `dbg.run(address=...)` and `dbg.step(until=...)` included.

### Changed

- **Breaking:** A `Stop` is one class with a subclass per kind, and each kind's part is on its own subclass, never `None` there: `Stop.Breakpoint` has `breakpoint` (a `BreakpointHit`, with `condition_error` and the breakpoint's `serial`), `Stop.Exception` has `exception` (`stop.exception.code`), `Stop.ModuleLoad` and `Stop.ModuleUnload` have `module`, `Stop.Bugcheck` has `bugcheck` (the code and parameters; `dbg.inspect.bugcheck()` analyzes it), and `Stop.Reload` (was `Stop.Reboot`) has `reload`. `match stop: case Stop.Breakpoint(breakpoint=hit):` and `isinstance()` narrow, and `stop.kind` names the class (`"module_load"`). A stop found at attach is the new `Stop.Entry`, not `Stop.Interrupt`. `stop.hit(bp)` replaces `bp in stop.breakpoints`; it compares the breakpoint's serial, so a later breakpoint that reuses the id, or another debugger's, is not the one hit.
- **Breaking:** `Exceptions.set(code, *, mode=None, command=None, disposition=None)` sets an exception's policy and returns its `ExceptionPolicy`, and the new `set_module_event("ld" | "ud", module=None, *, mode=None, command=None)` sets a module load or unload filter and returns its `ModuleEventPolicy`. `set("ld")` and `set("ud:<module>")` raise `ValueError`.
- **Breaking:** How a list walk ended is a `ListTermination` (was `ListEnd`), with a subclass per kind: `ListTermination.Cycle` has the `address` where the cycle closed, `ListTermination.Corrupt` the `error`, and every kind a `diagnostic`, why the walk stopped before the list head. A list such as `WdfQueueDetail.pending` stays a `list`, with `pending_stopped` beside it.
- **Breaking:** A stop's `thread` and `process` are `ThreadInfo` and `ProcessInfo` records, and its `cpu` is the processor number, so a stop is a snapshot that stays true: the collections take them as keys, as in `dbg.threads[stop.thread].backtrace()` and `dbg.cpus[stop.cpu].registers`. `when=` callbacks receive the same `Stop`.
- **Breaking:** `dbg.run_to()` and `dbg.cont()` are gone: `run(address=...)` runs to an address, `step(until=address)` and `step_over(until=address)` single-step there, and `run(disposition="handled")` resumes past an exception. `step()` and `step_over()` take `timeout` first and `until=` by keyword. `reboot()` and `crash()` wait for the stop and return it.
- **Breaking:** Results are records that behave as values, like frozen dataclasses: they compare with `==`, hash, and `match` their fields (`case ModuleInfo(name="nt")`), and are no longer mappings. Read a field as an attribute instead of `record["field"]`, and use `to_dict()` instead of `keys()`, `items()`, `len()` or iterating. The `Record` class is gone: name-keyed maps, such as `vmcs_fields()`, `SavedVtl.general_registers` and `VpRegisters.registers`, are plain `dict`s (`general_registers["rcx"]`).
- **Breaking:** Options are keyword-only: an SDK method takes what it is about (an address, a name, a record) by position, and its modes, flags and options by keyword, as in `exceptions.set("av", mode="break")`, `breakpoints.add(target, condition="...")`, `thread.backtrace(limit=8)`, `inspect.vring(address, module="viostor")`, `vtl.read(address, size, physical=True)` and `memory.read_unicode_string(address, bits=32)`. An address argument is named `address` everywhere (was `addr` on `Memory` and `Type.at()`), and `Memory.read()` takes `size` (was `n`).
- **Breaking:** A field or argument with a fixed set of values is typed as a `Literal` of snake-case names, which the REPL still prints in its own words: for example `"kernel_module"` for `AddressDescription.kind`, `"ntstatus"` for an error code's kind, `"no_pdb"` for `ModuleSymbols.status`, `"pde"` for a page-table level, and `"nonpaged"` for a pool type.
- **Breaking:** Many SDK classes have new names, one per model concept, shared with the REPL's records (`LoadedModule` is `ModuleInfo`, `ThreadSummary` is `ThreadInfo`, `MemoryRegion` is `MemoryRegionInfo`, and `MemoryRegion` is now a user-mode minidump's region, ...), and some fields moved: paths no longer repeat their parent (`thread.inspect().info.tid`, `heap.inspect().nt.header.index`, `dump.exception.info.code`, `report.power.record`, `region.info.base`), and `ModuleInfo.base` and `.timestamp` are the module's base and timestamp. The [SDK reference](https://ntoseye.com/reference/sdk/) lists each class with its fields.
- **Breaking:** Collections behave alike. Each iterates as a typed `Iterator[...]` (the `ProcessIterator`-style classes are gone), and `[]`, `get()` and `in` take its key, its item's record (`dbg.threads[stop.thread]`, `dump.threads[thread_info]`) or, for `in`, the item itself (`bp in dbg.breakpoints`). `get()`'s parameter is named `key`, and `at()`'s `address`. `Regions.at(address)` is `Regions.get(address)`, and `Threads.at(address)` returns `None` instead of raising when no thread has that `_ETHREAD`.
- **Breaking:** `dbg.breakpoints.watch()` returns a `Breakpoint`, whose `watch_access` and `watch_length` replace `Watchpoint.access` and `.length`; `Breakpoint.address` is `None` for a breakpoint that has not resolved. A one-shot breakpoint that fired is no longer listed: its handle's `valid` is `False` and `delete()` does nothing, and a new breakpoint, from the REPL or the SDK, can take its address.
- **Breaking:** The SDK names a processor by its number everywhere: `Stop.cpu`, `ThreadDetail.cpu`, `ThreadStack.active` and `FindStackThread.active` are the processor number (an `int`, or `None`), `VcpuInfo` has `number` instead of `id`, and `Cpu.number` replaces `Cpu.id`. `dbg.cpus` is a plain sequence that takes an `int`. `Cpu.info()` (`!cpuinfo`) is `Cpu.cpuinfo()`, and `Cpu.info` is the processor's `VcpuInfo` record, as on every handle.
- **Breaking:** `UserThread`'s thread-info stream fields (`start_address`, `create_time`, `exit_time`, `kernel_time`, `user_time`, `exit_status`, `affinity`) are in `UserThread.times`, a `UserThreadTimes` or `None`; `UserThread.stack` is a `CapturedStack` (`start`, `size`) instead of a tuple; and a user thread's identity is its `tid` (the `id` text is gone).
- **Breaking:** `Memory.describe(address)` always returns an `AddressDescription` and is refused on a user-mode minidump, whose region report is `UserDump.address_report()`. `Inspect.global_flags()` reads the flags, and `set_global_flags(change)` sets them.
- **Breaking:** The REPL refuses words a command does not take, with `<command>: unexpected argument '<word>'`, instead of ignoring them or printing the help: `vertarget x`, `k 3 extra` and `ln nt!KeBugCheckEx extra` now fail.
- Breakpoint actions (`bp ... "do"`) and exception filter commands (`sx -c`) run at every stop that triggers them, whichever host resumed the target: the SDK's `run()`, `wait()` and steps, the DAP adapter and the gdbserver run them too, not only REPL commands. In the SDK their output goes to `sys.stdout`. A breakpoint takes `when=` or `action=`, not both (`ValueError`).
- An exception that a notify filter (`sxn`) lets pass is reported as a notice on every host, in the REPL, the SDK's `dbg.notices()`, MCP and DAP, and its `-c` command runs.
- Ctrl+C during the SDK's `run()` or `wait()` breaks in and leaves the target halted, as it does during `command("g")`; it used to leave the target running.
- `.reboot` and `.crash` wait for the target's next stop and show it, and the SDK's `reboot()` and `crash()` return it. On a backend that cannot control the target, they say it needs target control support.
- The SDK checks a method as the REPL checks its command, with the same refusals: a run or step on a crash dump raises `the dmp backend cannot run or step the target`, and `hypercalls()`, `select_partition()`, `Driver.inspect()` and `Device.inspect()` need a kernel target. `write_dump()` shows `.dump`'s progress bar.
- On a crash dump or user-mode minidump, a command that writes memory or registers (`eb`, `ew`, `ed`, `eq`, `ef`, `ea`, `eza`, `!eb`, `!ed`, `!eq`, `f`, `r rax=1`) and the SDK's `Memory.write*()` are refused before they read their arguments, with `<command> is not applicable to a static crash dump`. `.pagein`, which runs the target to page memory in, says the backend cannot run the target, and it is refused in a breakpoint action, an exception command, and from GDB and DAP clients.
- `ib`, `iw` and `id` need a halted kernel target whose backend reads I/O ports, since reading a port can change the device: they are refused on a dump and while the target runs.
- `!address -SUMMARY` on a user-mode minidump, `!chkimg -D` and the `!ndiskd.nbl` switches are recognized in upper case, as WinDbg takes them; `!address -SUMMARY` failed with `Symbol 'SUMMARY' not found`. On a kernel target, `!address -summary` says it needs a user-mode minidump, and its usage shows that a kernel target takes an address. An unknown switch, such as `!chkimg /x` or `!gflag /x`, says so instead of being taken as a module or an expression.
- A command line that does not parse reports why, then the command's usage, so the usage in the error is the one `help` shows. `!reg q` and dx's `-v`, `-nv` and `, x`, which were accepted, are in their usage.
- `--plain-repl` scripts go on after a command fails, reporting the error, as the interactive REPL does; a failing command such as `!dbgprint x` used to end the script.
- `.thread .` selects the current thread, and `!thread` with a bad count says so instead of ignoring it.
- In the VTL1 view, `r reg=value`, `ob`/`ow`/`od` and the SDK's `Memory.write*()` are refused as read-only, and `.sympath`, `.reload` and `.fetchimage` work. At a stop in VTL1, the SDK refuses what the REPL refuses: memory writes and the methods that read NT's structures. In VTL1, `gh`, `gn`, `pc`, `tc`, `pt`, `tt`, `ph`, `th`, `bp` and the `sx` commands are accepted (a `bp` in VTL1 code is still refused), `!hvr` is refused in the `.vtl 1` view, and a refusal names the command as typed.
- `q` exits sooner, by 0.2 s on a minidump of a process with many modules loaded.
- `k` and `~*k` on a minidump that lacks a module's code ask the symbol server for the module's image once per session, as for PDBs, instead of at every stack walk when the server does not have it or cannot be reached; `.reload` asks again. Offline, ten `~*k` on an ARM64 minidump took 1.7 s and now take 0.3 s.
- `s` searches about ten times faster: 256 MiB of a user-mode minidump's address space in 45 ms instead of 420 ms.
- `--plain-repl`, the MCP server, the DAP adapter and the Python SDK start sooner: they build the symbol and type name indexes behind completion and symbol search when a search first needs them, not when the session starts. Opening a PowerShell minidump with `--plain-repl` takes 0.29 s instead of 0.39 s.
- Indexing a module's symbols is faster, so a dump with many modules opens about a third sooner: a PowerShell minidump opens with `--plain-repl` in 0.22 s instead of 0.29 s, and a charmap minidump in 0.10 s instead of 0.15 s.
- The `ntoseye` command and the Python package allocate memory with mimalloc, which makes opening a dump, `k`, and symbol searches about 15% faster. Indexing symbols takes more memory at its peak: about 1.3 GiB instead of 1.0 GiB for an ARM64 PowerShell minidump with 95 modules.
- A command's usage line in `help` and the command reference comes from what the command accepts, so it lists what some lines left out, such as `.process ... [eprocess|pid|0]`, `!apc [.|*|thread|process]` and the byte length of `c`, `m`, `f`, `s` and `.writemem`. A command with several forms shows one usage line for each, as `!alpc`, `!heap` and `.kdfiles` do.

### Fixed

## v0.45.0 (2026-10-03)

ntoseye can now debug the Windows hypervisor itself on Intel hosts. It can walk hypervisor partitions and virtual processors, inspect and disassemble guest memory, including WSL2, decode hypercalls and break on them based on the caller, and unwind hypervisor stacks. Kernel module unloads can now stop the debugger too, just like module loads.

### Added

- `sxe`/`sxn`/`sxd`/`sxi` `ud[:<module>]` stop on, report, or ignore kernel module unloads the way `ld` handles loads, with `-c` to run commands at the stop; the stop comes after the driver's unload routine, while the module is still listed with its symbols. The SDK has `Exceptions.module_events` and `Stop.ModuleUnload`; DAP reports the stop reason `module unload`.
- `~` accepts the vCPU id it lists in place of a processor number (`~p01.03s`, `~p01.03k`, `~p01.03r`), ignoring case.
- `Registers.get(name, default=None)` returns a register's value, or `default` when the register file (for example an unwound frame) does not hold it.
- `DisassembledInstruction` has `length`, `mnemonic` and `operands`; each `Operand` describes a register, memory, immediate or branch operand, so scripts no longer need to parse `asm`.
- `!hvpartitions` shows the Windows hypervisor's partitions as a tree with their privileges and each VP's processor, VTL, where it left off and its last exit; `!hvvps` lists a partition's VPs and the processors that run them. `~`, the stop line and the MCP trailer (`runs partition 0x4 VP 2`) name a vCPU that runs a guest partition (Hyper-V VM, WSL2, Sandbox) as `partition 0x4 VP 2`; the SDK's run status has it as `running_vp`. The SDK has `dbg.hypervisor_partitions()` and `VirtualProcessor.processors`. Hypervisor commands need the memory or gdb backend, or kd/kdnet with host memory, and say so otherwise.
- `!hvept <gpa>` (or `-v <address>` for a root virtual address) walks each VTL's extended page tables and shows the host address, access, page size and memory type; `!hveptdiff` lists the guest physical ranges VTL0 and VTL1 map differently. The SDK has `HypervisorVtl.translate()` and `VirtualProcessor.ept_differences()`.
- `!hvvmcs [-msr|-io]` shows every field of a VTL's Enlightened VMCS, the MSRs it intercepts or passes (named, e.g. `IA32_EFER`), and its intercepted I/O ports. The SDK has `HypervisorVtl.vmcs_fields()`, `msr_intercepts()` and `io_intercepts()`.
- `!hvd` reads and `!hvu` disassembles a guest partition's memory, virtual (4-level long-mode guests) or with `-p` physical. Like `!hvept`, `!hveptdiff` and `!hvvmcs`, they default to the VP the current processor runs. The SDK has `HypervisorVtl.read()`, `translate_virtual()` and `disassemble()`.
- `!hvcalls` lists the hypervisor's hypercall table with TLFS names, rep/variable-header flags, input/output sizes and handlers (`-a` includes unimplemented codes); `hv!` now has names for the hypercall handlers and `hv!VmExitEntry`, usable in `k`, `u`, `ln`, `x` and expressions. The SDK has `dbg.hypercalls()`.
- A saved VTL state shows the VM exit's qualification, interruption info and instruction length, and the guest's general-purpose registers recovered from the hypervisor's exit entry code, which `r`, expressions and stacks use. A state that may describe the previous exit is marked "(may be one exit behind)" and is not selected automatically; a hardware breakpoint on `hv!VmExitEntry` stops with a current state. The SDK has `SavedVtlState.general_registers` and `may_be_stale`.
- At a hypervisor stop, the stop header, `~` and `.vtlcxr` name the guest VP the processor serves and decode the hypercall being handled (code, TLFS name, flags); `!hvcall` shows its full input, including XMM fast calls, rep lists and extended GVA flush ranges with their addresses, page counts and page sizes. The hypercall page shows as module `hvcall` (`hvcall!Hypercall`, `hvcall!VtlReturn64`). MCP, DAP thread names and the SDK (`Cpu.serving`, `SavedVtlState.hypercall`) show the same.
- `!hvbp <call> [partition [vp]]` stops on a hypercall only from the given caller; its condition is evaluated on the caller's registers and reads the caller's memory, so `$pqwo(rdx)` tests a slow call's input. The SDK has `Breakpoints.add_hypercall()`, `Breakpoint.hypercall`, and `Cpu.hypercall_caller()`, which gives a `when=` callback the caller's registers, decoded call and memory.
- `!hvexit <reason> [partition [vp]]` stops on a VM exit by its reason (`cpuid`, `rdmsr`, `wrmsr`, `ept_violation`, or the number), only from the given caller; its condition sees the caller's registers at the exit, so `!hvexit wrmsr if @rcx==0x6e0` stops on writes of `IA32_TSC_DEADLINE`. The guest runs far slower while it is set, as every exit is checked, so a guest partition's VPs barely run and a filter on one rarely stops; `!hvbp` stops on their hypercalls. The SDK has `Breakpoints.add_exit()` and `Breakpoint.vm_exit`.
- `!hvr [partition vp [vtl]]` shows the registers of any hypervisor VP, such as a WSL2 VP blocked in `HLT` that no processor runs: those of the vCPU that runs it, of the exit a vCPU handles for it, or that it saved at its last exit. The SDK has `VirtualProcessor.registers()`.
- `.partition <id>` inspects the Windows guest of a hypervisor partition, such as a Windows Sandbox, in place of the target, read-only: `lm`, `!process`, `dt`, `u` and `k` read its kernel with its symbols, and its VPs are the threads. `.partition 1` returns to the target, and a partition that runs no Windows kernel, such as WSL2's, is refused with that reason. The SDK has `Debugger.select_partition()` and `Debugger.partition`; MCP's trailer says which partition is inspected.
- Hypervisor stacks unwind from the hypervisor's own unwind data when a copy of the running `hvix64.exe` is in the symbol cache or a local store (`.fetchimage /f <file>`, `Symbols.import_image()` add one), and otherwise from function prologs, marked `[prolog]`. The few functions whose unwind data leaves out their stack allocation, such as the external-interrupt exit handler from build 22621 on, unwind from their prologs too. The SDK's `Cpu.backtrace()` walks a processor's own stack, the hypervisor's when it is halted there, and with `vtl=` from where a VTL left off as the hypervisor saved it.
- `.vtlcxr 1` selects the state the hypervisor saved for VTL1, so `k`, `r`, `u` and expressions inspect the secure kernel where it left off (read-only); `.vtlcxr` returns to VTL0.
- In DAP, a vCPU halted in the hypervisor shows the hypervisor's own frames first, then a label frame, then the saved VTL state's frames.

### Changed

- **Breaking:** `Exceptions.module_loads` is replaced by `Exceptions.module_events`, which lists the unload filters (`sx* ud`) along with the load filters.
- **Breaking:** MCP's `command` tool no longer takes `format`, and rejects a call that passes it: it returns the REPL's text with its `[target ...]` trailer. For typed results, use the Python SDK.
- The hypervisor image is named `hv` as in WinDbg (`hv+0x…` instead of `hvix64+0x…`), and expressions accept `hv` in the hypervisor's context.
- On the gdb backend, software breakpoints in user space are refused (use `ba e1`); single steps into user space use debug-register sites, while a run to a user-space address (`p` over a call, `gu`) ends with an error. Previously stray `int3`s could be left in shared user code.
- Software breakpoints in the Windows hypervisor's code are refused with a pointer to `ba e1`, instead of left pending forever; NT breakpoints can still be set from the hypervisor's context.
- On the gdb backend, a breakpoint whose condition or filter declines many hits a second slows the target much less: a declined hit no longer rewrites the site journal on disk.
- On the gdb backend under VBS, single steps (`t`, `step()`, and the walks built on them, such as `wt` and `trace_calls`) are about 15% faster and use less host CPU: replies from the stub are read buffered, and a step no longer selects its vCPU again after the vCPU's own stop.
- `u` without an address works as in WinDbg: it starts at the instruction pointer, and continues after the previous `u` until the target runs or another frame, thread, or process is selected.
- `!peb`, `!teb`, `!gle` and `!dlls` no longer need `.process`: without one they decode the current thread's process, as in WinDbg.

- `t` after `~Ns` on kd/kdnet steps processor N instead of leaving it unmoved, and breakpoints on the stopped processor keep hitting afterwards; on ARM64 targets, stepping another processor is refused instead of hanging.
- Ctrl+C, a DAP `pause`/`disconnect`, or a server termination signal now break in on a step that never stops, instead of the session hanging until the transport times out; walks (`ta`, `pa`, `wt`, `step(until=)`) end on the first Ctrl+C.

A `Stop.Step` had seemed to say the walk ended on an instruction in NT even when it was broken into in the Windows hypervisor, where the next step was refused.
- Ctrl+C in the REPL now stops the target when a breakpoint whose hits are declined (condition, `/t` filter, other process) fires constantly.
- REPL errors from `g`, `t`, `r`, `~` and `.thread` show their message instead of an internal form such as `DebugInfo("…")`, and `bp` or `ba` on a backend that cannot set them names the backend instead of "the current backend does not support this".
- In DAP, a Debug Console command after one that moved the context (`.thread`, `.cxr`, `!thread`) runs instead of failing with "stale frame id" until the client walks the stack again.
- Code that profile-guided optimization split off from its function, far from every symbol, is named after that function through its chained unwind data (`nt!IopXxxControlFile+0x22bddf`) in stacks, disassembly, `ln` and the SDK's `symbols.nearest()`, instead of `nt+0xb1552f` or "no symbol found".
- `wt`, `p`, `gu` and the SDK's `step_over`/`step_out` no longer follow the wrong thread, wait forever for a thread that exited, or crawl under load on code every thread runs; a walk whose thread exits ends with an error.
- A gdbserver step or continue that cannot start now reports SIGINT, so gdb's `next`/`step` no longer loop.
- On the gdb backend, a `bp` on `nt!DbgLoadImageSymbols` (or the unload functions) now stops when no `sx` filter surfaces the event.
- On the gdb backend, the data address QEMU sends with a vCPU's next stop when that vCPU's watchpoint hit lost the race to another vCPU's stop no longer misclassifies the stop: a stop on an execute breakpoint is no longer mistaken for a plain stop, and a stop on a breakpoint is no longer reported as a data watchpoint's hit.
- On the gdb backend under VBS, a step or a resume from a breakpoint no longer gives up with "letting every vCPU run for 1s did not free it" when it should not. The debugger's own work between the vCPUs' runs counted against that second, and the first time a session finds a vCPU in the Windows hypervisor that work takes over half a second. And a vCPU waiting in an interrupt handler failed the step whenever the last run caught the handler in a call into the hypervisor, such as a spin loop's long-wait notification; the step now ends in the handler, as it does when the last run finds the handler in NT.
- On the gdb backend under VBS, a data watchpoint's hit that another vCPU makes while a step or a resume from a breakpoint lets the other vCPUs run is no longer lost: a step ends on it (`step()` returns that stop), and a resume reports it as its stop.
- On the gdb backend under VBS, a step or a resume from a breakpoint that waits on the other vCPUs no longer lets them run only a few milliseconds at a time when one of them is stopped on a breakpoint: that vCPU ended every run at once, and is now held for every other run.
- On the gdb backend under VBS, a step no longer ends in a guest partition's code (WSL2, a Hyper-V VM) when the Windows hypervisor runs that partition's VP on the stepped vCPU's processor while NT waits there, after which the next step failed with "Bad virtual address". The step waits for NT to run there again, and a step of a vCPU that runs a guest partition's VP is refused, naming the VP.
- `Breakpoint.delete()` no longer raises for a breakpoint that is already gone (such as a fired one-shot), and a stale handle no longer deletes a newer breakpoint that reuses its id.
- `.thread` on a thread whose vCPU is in the hypervisor selects where NT left off instead of the hypervisor's registers.
- `.vtl 0` after `.vtl 1` at a hypervisor stop returns to the stop's view instead of the hypervisor's registers.
- VTL1's saved state is listed even before the secure kernel was looked up.
- A saved VTL state is no longer reported as current after the processor has switched to another VTL or VP.
- `k` at a hypervisor stop no longer repeats addresses or lists NT addresses as hypervisor frames; scan frames are always marked `[scan]`.
